# 严苛循环优化（细节决定生死）

把「功能应用」打磨到真正好用：先对准目标，再改设计根因，并用小例子验证。  
读者可以是人（看懂规则），也可以是模型（按步骤执行）。

## 1. 核心指令（焚诀，原文不得改动）

参考「{建议内容}参考这个建议，」请针对{功能应用主轴中的功能}等所有功能，检查提取重点优化建议内容，找出提升{功能应用输出目的}的效果的观点和建议，要严苛的、真实的，为了能写出真正好用的{功能应用}！然后按照这些观点和建议进行仔细优化。{功能应用}是"细节决定生死"的行业，每一处小的改进，乘以10万用户，就是巨大的差异，因此我们要循环优化，直到能写出真正的爆款为止。

执行时把 `{…}` 换成本轮真实内容。

补充规则：

| 规则 | 怎么做 | 为什么 |
|------|--------|--------|
| 语气 | 禁止「可以考虑 / 或许更好」这类软化说法 | 软建议乘以大量用户仍等于没改 |
| 无外部建议 | 做自检时，去掉焚诀里「参考建议」那一段前缀，其余照旧 | 避免假装引用了不存在的材料 |
| 少记忆 | 续做下一轮时，只保留：最多 5 条「上轮已改要点」+ 当前对象原文 + 本轮新建议；不要粘贴上轮长文 | 多余上下文会淹没真正要改的点；必要时开新会话更干净 |
| 质量门槛 | 开始提取前先读 [references/harsh-bar.md](references/harsh-bar.md)。若产出命中其中的「必须打回」类型，整轮作废重做 | 防止格式看起来很勤快、实质没有变好 |

## 2. 选择模式

| 模式 | 什么时候用 | 步骤顺序 |
|------|------------|----------|
| **快循环**（默认） | 文案、Prompt、Skill、GUI、单个模块 | 对齐 → 提取建议 → 改对象 → 最小验证 → 自检是否改到位 |
| **工程闭环** | 复杂 Agent；或用户明确要求任务主轴 / 静态自检 / 动态质检 | 写清任务主轴 → 静态自检 → **仅当已有运行记录时**做动态质检 → 再按快循环落地修改 |

- 没有真实或仿真的运行轨迹时：写明 `动态：跳过（无轨迹）`，**禁止编造**测试分数或假轨迹。  
- 工程闭环的细则按需阅读：[references/engineering-loop.md](references/engineering-loop.md)（不要把该文件整篇贴进对话）。

## 3. 默认行为

- 默认：**找出问题并直接改对象**（改文件或给出完整新文稿）。  
- 用户说「只诊断 / 先别改」：只输出建议表和「扔掉清单」，不改文件。  
- 改动很大或难回滚：先改一个小样例，确认方向后再铺开。  
- 同一对象连续优化默认最多 3 轮；本轮只要还改了东西，默认**还没**达到「可以停」的爆款标准。  
- 若连续两轮都提不出新的 P0（只剩文风或排版游戏）：停止密炼，给出维护建议。  
- 用户给了很长的方法论：只抽取可执行原则，禁止整篇粘贴进回复。

## 4. 四个必填信息（槽位）

开始前对齐这四项。缺了就先问清或合理推断并复述确认。

| 槽位 | 含义 | 缺失时怎么做 |
|------|------|----------------|
| `{功能应用}` | 正在优化的对象是什么 | 从上下文推断，并复述给用户确认 |
| `{功能应用主轴中的功能}` | 主路径上必须做好的能力列表；尽量补 1–3 条「绝不能做」 | 先列出主轴，再优化；禁止只改顺眼的几项 |
| `{功能应用输出目的}` | 用户用完应得到什么结果；最好带一个能感知的小例子 | 追问「用完得到什么」 |
| `{建议内容}` | 外部反馈、运行结论、或上轮已确认的要点 | 向用户索取；或声明「无外部建议，仅基于现状严苛自审」 |

冲突时：以**输出目的**和「绝不能做」为准，冲突的建议放进「本轮扔掉」并写明原因。  
优化 GUI 时：先根据主轴列出检查清单，**逐项完成**；未完成不得宣称已达爆款。

## 5. 工作步骤

### 步骤 0 — 对齐

- 第一轮：用 3–6 行写清四槽位、模式、主轴列表。  
- 续轮：只写本轮变化 + 最多 5 条上轮已改要点。  
- 若对象已有文件/正文/Prompt：先读现状，禁止凭记忆瞎改。

### 步骤 1 — 提取建议

对主轴上的**每一项**能力过目。优化表默认只收 **P0 / P1**（定义见 harsh-bar）。

每一条保留的建议必须同时写清：

1. **设计杠杆**：改哪里（哪段 Prompt、哪条规则、哪个默认行为）；  
2. **失败类型**：能修好哪**一类**问题（不是只修某一个编号案例）。

缺任何一项 → 视为假根因，打回。

额外要求：

- **缺口义务**：即使用户已经写全了建议和禁忌，仍要再挖至少 1 条「用户没写、但大量用户会踩」的坑（例如字段歧义、空结果怎么处理、索取 vs 执行人）。若只会复述用户原话，说明增量不够，继续挖。  
- **规则别过刚**：写下死规则前，用一句话自问副作用——会不会把合法灰区（如「甲向乙要资料」）误判成乱派工？会，就改成更细的字段，而不是一刀切。

### 步骤 2 — 落地修改

按优先级 P0 → P1 修改**对象本身**。

| 对象类型 | 交付方式 |
|----------|----------|
| 文件 / 代码 / Skill | 直接改仓库里的文件 |
| 文案 / GUI（无文件） | 在回复里给出完整改后正文；GUI 同步勾检查清单 |
| Prompt / Agent 设计 | 给出可整段复制的完整新稿，外加极短说明（对应哪几条建议） |
| 只诊断 | 不改，只交表 |

### 步骤 3 — 最小验证与贯彻自检

以下三项缺一不可，否则打回：

1. **改前伤口**：用同一个小例子说明旧版会错成什么样（可点名会编造或冗长的句子类型）。  
2. **改后试跑样例**：按**新版本**，对同一例子写出助手可能输出的**全文**（禁止只写「应该会更好」）。  
3. **对照目的**：说明样例为何更接近输出目的；若样例仍违规，先改对象再交付。

没有现成例子时，先构造 1 个最小例子再验证。  
贯彻自检：每条 P0 是否改到了设计杠杆、是否只换了同义词、有没有引入新问题。  
最后用**一句话**对比新旧版本好在哪里。

### 步骤 4 — 是否继续

- 下一轮只处理新问题，禁止重复已落地的条目。  
- 命中 harsh-bar 的打回类型，或触发「连续两轮无新 P0」停损 → 停止。  
- 用户说停 → 立即停，交出当前最佳结果。

## 6. 每轮怎么写给用户看

**快循环（默认，短）：**

```markdown
## 对齐（写明模式）
## 建议表（P0/P1）与本轮扔掉（可很短）
## 改动说明 / 改后全文或文件路径
## 最小验证（改前伤口 + 改后试跑样例全文 + 对照目的）
## 一句话对照 + 是否继续或停止
```

**工程闭环，或用户要求完整审计时**，再增加：主轴过目表、动态执行或跳过、逐条贯彻自检、是否达到可停止标准。

报告篇幅不得超过改动本身；否则视为「用长报告冒充努力」，打回。

## 7. 态度

目标是让对象更好用，不是写出更长的评审。  
细节默认有问题，直到证明对输出目的无害，或已经被修好。
