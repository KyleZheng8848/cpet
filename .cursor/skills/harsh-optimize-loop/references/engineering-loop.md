# 工程闭环（仅在需要时阅读）

只在选择 **工程闭环** 模式时使用本文。  
执行时仍遵守主文件 `SKILL.md` 里的焚诀与产出结构。  
**不要把本文整篇粘贴进对话**——按当前阶段读对应小节即可。

工程闭环把复杂 Agent / 复杂功能应用的优化分成几个阶段，避免一上来就海量试跑、或只凭感觉改 Prompt。

---

## 阶段 0：任务主轴（评判一切的基准）

先写清楚，并在后续阶段反复对照：

1. **是什么**：角色、服务对象、核心价值  
2. **做什么**：核心任务流程、必须完成的能力  
3. **不能做什么**：禁忌与红线  
4. **行为准则**：多目标冲突时优先谁；输出风格；遇到歧义或失败时怎么处理  
5. **成功标准**：1–3 个小例子的名字或摘要 + 用自然语言说明「什么算好」

设计原则（简记）：

- 先描述理想结果，再逐步收紧约束（先宽后窄）。  
- 按真实用户路径想问题，不要只按技术模块切。  
- 主轴提供判断框架，不必穷举所有情况。  
- 每条原则最好能对应到可测的小例子；测不了就写得太虚，需要具体化。

主轴可以改，但需要**多条独立证据**，不能因为一个刁钻例子就改方向。改主轴后，要回头检查已有设计是否仍然成立，并记下改因。

初步搭好 Prompt / 工具 / 流程后：先做静态自检，不要立刻堆大量测试噪声。

---

## 阶段 1：静态自检（不运行系统）

在不真正跑 Agent 的前提下，用焚诀 + 任务主轴审查当前设计（Prompt、工具说明、流程）。

建议检查的方面：

1. 是否忠实反映任务主轴  
2. 各条规则之间是否互相打架  
3. 能力边界是否清楚，有没有灰色地带  
4. 工具是否可能被误用，或在不该用时被调用  
5. 异常输入、失败、极端情况有没有被想到  
6. 措辞是否含糊，模型可能误解  

严重程度怎么处理：

| 级别 | 含义 | 动作 |
|------|------|------|
| Critical（严重） | 伤核心能力或违反主轴 | 必须修；修好后从当前轮审查重心重来 |
| Major（重要） | 伤重要能力或体验 | 本轮修掉并记下改了什么 |
| Minor（次要） | 细节，不影响主功能 | 记下，不阻塞前进 |

可做多轮静态自检，侧重点可以是：全面扫描 → 盯住改动最大的区域并推演几段对话 → 故意想对抗性/失败/多目标冲突。  
若新建议开始明显重复、变空 → 在有条件时进入动态质检。

---

## 阶段 2：动态质检（必须有运行记录）

**没有**真实或高度仿真的运行轨迹时：整段跳过，写 `动态：跳过（无轨迹）`，去补案例后再做。禁止编造。

有轨迹时，建议准备约 5–8 个例子，覆盖：

- 主干路径（最常见）2–3 个  
- 边界、对抗、复杂路径各 1–2 个  

记录时尽量包含：意图判断 → 是否调用工具及参数 → 如何处理返回 → 最终输出 vs 理想输出 → 偏差从哪一步开始。

分析时要跨多个例子找**共同模式**和**设计层根因**，不要写成「只修某一个例子」。  
改完后做贯彻自检，并做改前 / 改后对比，识别「看起来改了、机制没变」。

---

## 阶段 3：循环演进与何时停止

随着成熟度调整重心：

1. **地基**：主干场景做对  
2. **健壮**：边界与异常也能体面处理  
3. **精炼**：表达与体验  

可以停止密集优化的信号（宜多条同时出现）：

- 连续静态自检挖不出新的设计层问题  
- 动态质检里的偏差模式越来越少，剩余多为次要且无共同根因  
- 行为与任务主轴一致，改一处不会处处坏  
- 每轮收益明显变小  

之后转为定期抽查、吸收真实新案例，而不是无限密炼。

---

## 阶段 4：认知升级（可选）

仅在一个项目告一段落、用户明确要求复盘时做：提炼 3–5 条可带到下一个项目的原则（写清适用场景与反面例子）。  
**默认不要在每一次调用里展开本阶段。**

---

## 与模型协作时的短提醒

- 每次修改前给足：任务主轴 + 当前设计 + 本轮结论（不要塞无关历史长文）。  
- 改完要求对照建议做自检。  
- 高风险改动：先让模型预判副作用，再执行。  
- 重要修改前用一句话留下版本快照（改了什么、为了解决什么）。
