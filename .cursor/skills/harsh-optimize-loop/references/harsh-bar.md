# 质量门槛与必须打回的情况

在提取建议、验收结果前阅读本文。  
拿不准一条建议该不该保留时：**扔掉**，不要塞进优化表。  
若本轮产出命中下方「必须打回」——整轮作废，重新做。

## 什么叫「值得保留的改动」

一条建议或改动需要同时满足：

1. **对准目的**：说得清它如何帮助用户达成「输出目的」。  
2. **用户能感到**：正常使用时能察觉差异，不是只有作者自己知道。  
3. **可执行**：写明改哪里、改成什么。  
4. **经得起放大**：想象使用次数很多时，这处问题会反复烦人，还是几乎无感。  
5. **根因级**：同时写清「设计杠杆」+「能覆盖的一类失败」；不是只修某一个案例。

## 优先级（P0 / P1 / P2）

| 级别 | 含义 | 是否进入优化表 |
|------|------|----------------|
| P0 | 挡住输出目的，或违反「绝不能做」；不改就会被当成不好用 | 必须进入 |
| P1 | 不挡主路径，但使用次数一多成本很高（多余步骤、歧义、不稳定） | 必须进入 |
| P2 | 锦上添花 | 默认不进入（除非用户明确要求） |

## 必须打回的产出形态

| 类型 | 典型样子 | 为什么废掉 |
|------|----------|------------|
| 过目表演 | 主轴全写「没问题」，但正文明显空泛或危险 | 等于没检查 |
| 假根因 | 把「语气更专业」说成根因，却说不清改哪条规则、修哪类失败 | 无法落地 |
| 单案例补丁 | 「只让第 3 个例子改成某句固定回答」 | 容易顾此失彼，越补越脆 |
| 报告重于改动 | 章节很多，对象几乎没变 | 用形式冒充进展 |
| 表面服从 | 只换同义词，机制不变 | 对目的没有增益 |
| 假验证 | 只写「更好了」，或只写「应接近…」却没有试跑样例全文 | 没有真正验证 |
| 复述无增量 | 用户给的禁忌又抄一遍，没有挖出新坑 | 相对普通助手没有额外价值 |
| 规则过刚 | 一刀切字段，把合法灰区打成错误（如把「甲向乙要资料」误判成乱派工） | 制造新伤 |
| 伪造动态 | 没有运行记录却编造测试分数或轨迹 | 用假证据带偏决策 |
| 软化或灌水 | 「或许可以」；或续轮把上轮长表再贴一遍 | 不落地 / 违反少记忆 |

## 常见空话（放进「本轮扔掉」，不要进优化表）

- 正确但无改法：「要重视用户」「加强体验」  
- 形容词堆砌：「更智能 / 更优雅 / 更有调性」（未绑到目的）  
- 为了显得听话而硬改，结果变差  
- 只改顺眼的功能，主轴其余未检查  
- 建议与输出目的冲突却仍采纳  
- 把事项标成「本轮不做」却说不清为何不挡目的  

## 不同对象时多看一眼

| 对象 | 额外注意 |
|------|----------|
| Agent | 没有运行轨迹就不要假装做过动态质检；优先查工具误用和能力边界灰区 |
| Prompt | 交付必须整段可复制；失败情况和禁忌写清楚 |
| Skill | 续轮只保留短要点；`description` 触发范围不要写得过宽 |
| 文案 / GUI | 主路径要一眼能懂；GUI 的检查清单勾完才能宣称可停止 |

## 停止前的复读（用挑剔用户的口吻）

- 第一眼是否知道能干什么、干完得到什么？  
- 主路径是否有多余步骤、术语或死胡同？  
- 失败、空白、边界情况是否体面？  
- 是否做过改前 / 改后验证？  
- 续轮是否简短，并且只处理新问题？  

仍有新的 P0，或打回项未清除 → **未达标**，继续改。
